B-roll: shared analysis, better discovery

Repository review · 16 September 2026 · Proposal only

Recommendation: share the long-form backend's resumable visual execution and reusable evidence with B-roll. Keep B-roll-specific interpretation and placement. Prioritize finding exact useful ranges over replacing one analysis prompt with another.

What is already shared

The Media Library invokes subtitler.media_analysis through frontend/src/main/mediaAssetAnalysis.ts. The long-form visual provider in subtitler/editorial_visual.py subclasses that same OpenAI media-analysis provider, and the editorial backend calls the same analyze_media function. Sampling, structured responses, and boundary refinement already have a common foundation.

The long-form orchestration in subtitler/editorial_hosted.py::_analyze_editorial_visual_windows adds bounded windows, saved progress, concurrency controls, and subdivision after malformed or incomplete structured responses. Its prompt finds meaningful events. The library prompt deliberately groups footage into broader editorial categories and describes retrieval value.

These interpretations serve different purposes. A menu transition may be essential to a story but unsuitable as illustrative footage; conversely, a quiet landscape may be excellent B-roll without being an important story event. Routing every library asset through the entire editorial pipeline would add unnecessary dependencies and work.

Suggested data flow

Design direction: make structured, labeled scene records the shared contract between video analysis and B-roll discovery. The existing analyzer already returns observed_label, time bounds, descriptions, tags, category, and confidence. However, the library's segment persistence and B-roll catalog projection currently omit observed_label as a dedicated field. Preserve it end to end instead of flattening the useful evidence into prose.

Keep broad category labels alongside specific event labels: “gameplay” filters the footage type, while “dodging an enemy attack” identifies a useful moment. Each record should retain asset and scene IDs, start/end times, the observed label, subjects/actions where established, evidence references, uncertainty, and analysis provenance. B-roll suitability and project-specific placement reasons should remain separate annotations. Labels inferred from sparse samples need candidate verification before being treated as exact clip boundaries.

The first implementation slice should therefore carry structured scene labels from analysis through library storage, retrieval, and candidate previews, with a compatibility adapter for existing library segments. Reuse existing editorial scene records when their media identity and evidence contracts match; generate B-roll-specific suitability only when needed. This makes richer retrieval possible without first replacing the entire backend.

Source context → editorial need → indexed range search → candidate verification → placement → review/export.

A useful need should specify what the viewer should see, why it helps, the desired duration and tone, exact entities, and exclusions. For example: “Show the dodge avoiding an attack for roughly four seconds,” rather than “combat gameplay.” Candidates should carry the observed action, source interval, matching evidence, uncertainty, and usable duration.

Separate reusable observations (“character moves away as an enemy attacks”) from use-dependent interpretation (“useful to explain dodging”). This lets different projects reuse the evidence without treating a previous project's narrative conclusions as facts. Import compatible evidence from already-analyzed source recordings into the library; do not require another full paid analysis merely to make it searchable.

Cache compatibility should include media fingerprint, analyzed interval, sampling policy, provider/model, analysis profile and schema/prompt version, plus locale/context where those affect interpretation. Existing library analysis runs already record provenance and fingerprints; build on that. Preserve user descriptions and locked ranges when importing or refining AI results.

Implementation sequence

  1. Fix discovery coverage and associations. Remove query-independent exclusions, rank ranges, window long transcripts, and correctly link web candidates to needs. Make omitted needs and insufficient evidence visible in diagnostics.
  2. Extract shared visual execution. Move windowing, resume, progress, and recovery into a reusable service while preserving the distinct analysis profiles. Generate estimates from the backend's actual sampling plan rather than maintaining matching formulas in TypeScript and Python.
  3. Reuse evidence and verify finalists. Import compatible editorial observations, add denser analysis of uncertain shortlisted intervals, and use source visuals when deciding where inserts belong. Run paid work only within explicitly authorized budgets.
  4. Improve editorial choice. Add alternatives with short previews, explicit crop/audio handling, and selection across the whole timeline to avoid repetitive footage. Compare semantic retrieval against the lexical baseline before making it the default.

How to judge success

Use a small preserved set of real needs and labeled useful ranges: exact actions, English/Japanese aliases, misleading filenames, brief events, repeated gameplay, long transcripts, and footage that should not receive B-roll. Measure whether a valid range appears in the top candidates, whether the selected interval actually shows the requested event, placement acceptance, correction effort, repetition, elapsed time, and paid cost. Evaluate discovery separately from placement so a good candidate rejected by the editor is distinguishable from a retrieval miss.

Behavior tests should cover visibility filters, full catalog/transcript coverage, exact interval bounds, locked user annotations, resume after interruption, stable need associations, and source-video protection. Run the repository's backend and frontend verification suites for the surfaces changed. Review the earliest affected editorial checkpoint boundary before implementing shared behavior changes; visual interpretation changes generally start at visual_learning. B-roll-only changes should not invalidate unrelated editorial artifacts.
